# 点云接口与坐标系现状核实

> 本文只记录**核实结果**与**推荐方案**，本次不修改点云接口、不新建 `mapmos_ros2`、
> 不添加任何 static TF。所有结论均来自当前工作区源码，行号对应核实时的文件状态。

## 1. 当前点云链路（已核实）

```text
NA70 UDP:2368
      │
      ▼
double_wedge_driver_lidar                      （src/inno_device_lidar_node.cpp）
      │  每包 200 点，累计 100 包后一次性发布
      ├─► /lidar_data    LidarScanBundle    内含 PointCloud2[100]，frame_id = lidar_frame
      ├─► /livox_data    CustomMsg          私有 Livox 兼容格式，frame_id = lidar_frame
      └─► /livox_status  LidarStatus        frame_id = lidar_frame
      │
      ▼
double_wedge_driver_test_lidar                 （src/test_lidar_driver.cpp）
      │  订阅 /lidar_data，将 100 个 PointCloud2 合并为一个
      └─► /inno_lidar_cloud  sensor_msgs/PointCloud2，frame_id = lidar_link
```

毫米波为独立支路，与激光链路无耦合：

```text
串口 → double_wedge_driver_radar               （src/inno_device_radar_node.cpp）
      ├─► /radar_data    sensor_msgs/PointCloud2，frame_id = map
      ├─► /radar_msg     RadarMsg，frame_id = map
      └─► /radar_status  RadarStatus，frame_id = map
```

### 1.1 核实要点

| 项 | 核实结果 | 位置 |
|---|---|---|
| 主驱动是否发布标准 `PointCloud2` | **否**。只发布私有 `LidarScanBundle` / `CustomMsg` | `inno_device_lidar_node.cpp:502-504` |
| `LidarScanBundle` 内部是否含标准点云 | **是**，字段为 `sensor_msgs/PointCloud2[] clouds` | `msg/LidarScanBundle.msg` |
| 唯一的标准 `PointCloud2` 激光话题 | `/inno_lidar_cloud`，由合并节点产生 | `test_lidar_driver.cpp:39,77` |
| 合并节点是否做坐标变换 | **否**。只做 `combined_cloud += cloud` 后改写 `frame_id` | `test_lidar_driver.cpp:66,73` |
| 坐标变换实际发生位置 | 在**主驱动内**，凑满 100 包后统一施加 pitch/yaw 补偿 | `inno_device_lidar_node.cpp:383-397` |

## 2. `frame_id` 实际取值与 launch 覆盖情况（已核实）

| 节点 | 参数默认值 | launch 默认值 | 可否被覆盖 |
|---|---|---|---|
| `double_wedge_driver_lidar` | `lidar_frame` (`:491`) | `lidar_frame` (`start_lidar.launch.py:11`) | 可，`frame_id:=` |
| `double_wedge_driver_test_lidar` | `lidar_link` (`:33`) | `lidar_link` (`test_lidar.launch.py:19`) | 可，`frame_id:=` |
| `double_wedge_driver_radar` | `map` (`:396`) | `map` (`start_radar.launch.py:14`) | 可，`frame_id:=` |

RViz2 配置 `config/inno_lidar_rviz.rviz` 的 `Fixed Frame` 为 `lidar_link`。

### 2.1 合并节点只改名不变换 —— 性质判定

`test_lidar_driver.cpp:58-73` 把 `frame_id` 从 `lidar_frame` 改写为 `lidar_link`，
但没有调用 `pcl::transformPointCloud`，即**两个坐标系名被当作同一个坐标系使用**。

经与 ROS1 原工程比对，该行为**是从 ROS1 继承的既有行为，不是本次迁移引入的回归**：

- ROS1 `src/test_lidar_driver.cpp:59` — `cloud.header.frame_id = "lidar_link";`
- ROS1 `src/test_lidar_driver.cpp:81` — `cloud2.header.frame_id = "lidar_link";`
- ROS1 主驱动 `:515,554` — `bundle_.clouds[i].header.frame_id = "lidar_frame";`

因此当前 `lidar_frame` 与 `lidar_link` 之间事实上是**零位姿关系**，但这个零位姿
从未被显式声明，也从未被实测确认。

**本次不做的处理及原因：**

- 不把两个字符串简单统一。统一字符串会把"尚未确认的坐标关系"伪装成"已确认相同"，
  掩盖真实的外参问题。
- 不添加 `lidar_frame → lidar_link` 的零位姿 static TF。当前没有任何实测或图纸依据
  证明两者外参为零，凭空发布零位姿属于捏造外参。

## 3. 两类显示问题必须区分

这是两个**性质不同**的问题，不能混为一谈：

### 3.1 `/lidar_data` —— 私有消息的显示限制（与 TF 无关）

`LidarScanBundle` 是本包自定义消息，RViz2 没有对应显示插件。无论 TF 是否连通，
RViz2 都**无法直接显示** `/lidar_data`。这是消息类型问题，不是坐标系问题。

要在 RViz2 中看到激光点云，当前**必须**经过合并节点产出的 `/inno_lidar_cloud`。

### 3.2 `/radar_data` —— 标准点云的 TF 连通性问题

`/radar_data` 是标准 `PointCloud2`，RViz2 有插件可显示，但其 `frame_id = map`
与 RViz2 的 `Fixed Frame = lidar_link` 之间**不存在任何 TF 链路**，当前工程也没有
任何节点发布 TF。同时启动激光与毫米波并使用现有 RViz2 配置时，`/radar_data`
预期会报 TF 查找失败。

另需注意：毫米波节点把测距结果放在 `(distance, 0, 0)`（`inno_device_radar_node.cpp:322-326`），
这是**传感器自身坐标系下的一维测距**，把它标为 `map` 在语义上就是错的——`map`
通常表示世界坐标系。该命名同样继承自 ROS1（原码 `cloud_msg.header.frame_id = "map"`）。

## 4. MapMOS 输入方案对比与推荐

设计文档要求 MapMOS 消费标准 `sensor_msgs/msg/PointCloud2`
（《开发文档》§7.2、《执行计划》§5.4）。需要说明的是：**该要求约束的是 MapMOS 的输入接口，
上游驱动内部使用私有消息并不违反这一要求**，只要在进入 MapMOS 之前存在标准点云即可。

### 方案 A：主驱动直接发布标准 `PointCloud2`

在 `double_wedge_driver_lidar` 内部增加一路合并后的 `PointCloud2` 发布。

- 优点：少一次「序列化 100 个 PointCloud2 → 传输 → 反序列化 → 合并」的往返；
  驱动在凑满 100 包时数据已在内存中，合并几乎零额外成本；链路延迟更低；
  Orin Nano 4GB 上 CPU 与内存拷贝压力更小。
- 缺点：需要改动**当前唯一尚未完成实机验收的节点**。阶段①的验收对象就是这个驱动，
  在实机收包验证通过前改动它，会使已进行的验证作废并引入新的风险面。

### 方案 B：将现有合并节点正式化（**推荐**）

把 `test_lidar_driver.cpp` 从"测试节点"提升为正式的点云适配节点。

- 优点：
  1. 合并逻辑**已经存在并可用**，不需要新写数据通路；
  2. **不改动驱动**，阶段①的实机验收可以照常推进，不被 MapMOS 工作阻塞；
  3. 与《开发文档》§8 的架构一致——该文档本就规划了独立的 `pointcloud_adapter_node`
     位于驱动与 MapMOS 之间，承担字段检查、NaN 清理、ROI 裁剪等职责；
  4. 驱动对现有私有消息消费者的接口契约保持不变。
- 缺点：多一跳节点间传输。整包 `LidarScanBundle`（100 × PointCloud2）需完整走一遍
  序列化/反序列化。

### 推荐结论

**阶段①先采用方案 B**，理由是它不改动待验收的驱动，且与既定架构相符。

**待实机测出真实包率与整包中继开销后再决策是否转向方案 A。** 若实测显示整包中继在
Orin Nano 上占用不可接受，建议的演进方式是在驱动内**增加**一个由参数开关控制的
合并点云发布（例如 `publish_merged_cloud`），而不是删除 `LidarScanBundle`——
后者会破坏现有消费者。

本次**不创建** `mapmos_ros2`，**不修改**任何点云接口。

## 5. 待确认事实与待定坐标关系

以下条目在进入 MapMOS 阶段前必须确认，不得无限后置：

### 5.1 坐标系与外参

- [ ] `lidar_frame` 与 `lidar_link` 是否确为同一位姿。若是，需明确保留哪一个名字，
      并说明另一个名字的存在理由；若否，需给出实测外参。
- [ ] 毫米波的正确 `frame_id`（当前的 `map` 语义错误），以及毫米波相对激光的安装外参。
      在外参可得之前，不发布 `map` 与激光坐标系之间的 TF。
- [ ] NA70 原始坐标方向是否符合 ROS 约定（+x 前 / +y 左 / +z 上）。
      当前驱动做了 `x=z, y=-x, z=-y` 的轴重排（`inno_device_lidar_node.cpp:338-341`），
      该重排的正确性需在 RViz2 中实测确认。
- [ ] 是否需要 `base_link`，以及 `base_link → 各传感器` 的静态 TF 由谁发布。

### 5.2 时间戳语义（影响 MapMOS 多帧组织）

核实中发现的时间戳细节，需在 MapMOS 阶段前明确：

- 每个 packet 的 `PointCloud2` 各自携带**该包自己的**时间戳（`:378`）；
- `LidarScanBundle.header.stamp` 取的是**第一个**包的时间戳（`:365`）；
- 合并节点输出的 `/inno_lidar_cloud.header.stamp` 取的是**最后一个**非空包的时间戳
  （`test_lidar_driver.cpp:67,74`，循环内反复覆盖）。

即：一帧合并点云横跨 100 个 packet 的采集时间，而对外只呈现其中一个时刻。
《开发文档》§48 已就双楔镜扫描的时间结构提出风险；此处需确认：

- [ ] 100 包对应的实际时间跨度（ROS1 注释标注 `cache_packet_count = 100 // 10Hz`，
      该 10Hz 为继承自 ROS1 的未验证假设）。
- [ ] 合并点云应采用首包、末包还是包中值作为 `header.stamp`。
- [ ] 是否需要保留逐点时间以支持后续 deskew。当前 `CustomPoint.offset_time`
      是按 `i * 5000 + 包序 * 1000000` 推算的合成值（`:358`），**不是**实测的逐点采样时间。

### 5.3 阶段①验收前必须完成（不得因本次未改接口而略过）

- [ ] `/inno_lidar_cloud` 在实机上持续发布，`ros2 topic hz` 稳定；
- [ ] 实机记录 `PointCloud2.fields` 到 `docs/NA70_POINTCLOUD2_FIELDS.md`；
- [ ] 时间戳持续递增，无跳变、无回退；
- [ ] `frame_id` 稳定，RViz2 无持续 TF 报错；
- [ ] 点数符合预期（每包 200 点 × 100 包 = 20000 点/帧，需实测核对）。
