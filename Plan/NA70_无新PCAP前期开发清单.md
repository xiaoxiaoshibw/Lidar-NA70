## 2. 本轮落地的可复核基线

- 新增 `packages/na70_core/` 可编辑安装包。`RayBatch` 按原始射线对齐保存码、XYZ/intensity、采集 SHA、帧/包/帧内点 ID、包级设备/抓包时间以及有效回波/方向可恢复掩码；构造时复制并只读化数组。零距离且角码可恢复时仍为已知方向，零距离且双角码为零为未知。
- `backend.decoder` 仍是唯一经典 PCAP 协议读取入口；其坐标计算与 S0 合成审计改用同一 `na70_core.geometry`。未补造逐点时间。旧 W1 的原始 NPZ 在**新运行**中增加 `direction_known_mask`，逐包/逐窗指标增加已知/未知方向数；旧证据只读保留。
- 基线 Git HEAD：`3e21ede34d11c026960c263911a5ee230b544e9b`，当前工作区另有大量未提交改动，不能把 HEAD 当本轮源码版本。Windows Python 3.12.10、Node.js 24.14.0；`1.pcap` SHA-256 `b17d7c17926e670b3d89ba0774c4140feb810e4935971ab57760f4bdd00636cd`，`2.pcap` SHA-256 `39899e0fb25c98a6dd2f2e5a1831b5256904fc23ae730ef9166329be845f8db7`。
- 在 Windows 本机运行：`web/.venv/Scripts/python.exe -m pytest tests/test_na70_core.py tests/test_decoder.py tests/test_thin_wire.py tests/test_wire_api.py tests/test_wire_scene.py -q`，**48 passed**。另将 HEAD 旧解码器与当前实现直接逐点对照：`1.pcap` 109,200 条、`2.pcap` 110,800 条（各取首/中/末帧、两种安装方向），全部 `array_equal`；两份文件按安装方向 1 完整解码的 43,910,000 条射线输出哈希也与旧版相同。安装方向 2 的全片对账仍待完成。当前短批次微基准未见加速，详见[验证记录](../web/VALIDATION.md)。此处所有导线场景夹具均为 `SYNTHETIC`。

## 3. 接下来的实施步骤

1. **收口 P0**：定义并校验 `wire-truth-v1`、`wire-run-v1`、`wire-stage-trace-v1`，固定字段、版本、拒绝原因和向后兼容；对原始 ID 与采集 SHA 做完整性测试。每个输出只允许引用真实存在的原始射线。
2. **完成 P1**：把 W1 已验证的 `packet_timeline`/`select_window` 提炼为纯核心的增量、受限时间窗，保留兼容入口；对分块、重复时间、缺时、倒退、间隔、末尾不足 100 包做对账。正式解码入口迁移前先运行全片逐点比较。
3. **完成 P2**：在执行阶段记录 Trace，不从最终统计反推；为排队/运行/失败/重启及取消明确持久化状态，限制并发、原始窗口和显示抽样上限。W1 仍只输出 `NOT_EVALUATED`。
4. **完成 P3**：UI 增加真值草稿与 reviewed 状态、同捕获两次运行对比和首个阻断阶段；所有图/表/点按 `run_id/window_id/capture_sha256` 校验。浏览器测试覆盖切换运行、慢响应、损坏数据和重启回看。
5. **准备采集卡**：记录安装姿态、线径/材质/朝向、独立线位与误差、静止依据、同机位背景、设备设置和原始哈希。收到新数据后先跑 W1，不自动推进拟合。

每一步保留旧入口和旧失败证据，按[开发执行规范](05_开发执行规范.md)保存环境、命令、哈希、指标及失败项。不得清理当前无关工作树改动；不把本机/WSL 结果写成 Jetson 验收。
